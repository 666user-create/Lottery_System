# 中奖履约(领奖 → 发货 → 签收)设计

> 状态:🚧 **后端已实现并验收通过**;前端页面进行中(见第十二节)
> 背景:评审反馈"抽奖后只发邮件、抽到了却没有发货",本质是**业务闭环缺了兑奖履约环节**。
> 设计原则:**最大化复用现有工单体系**,不新建履约模块。
> 已定决策:① 历史中奖记录一律视为「未领取」;② 保留「确认收货」环节(4 状态闭环);
> ③ **客户端保留「我要领奖」申请入口,管理端拥有完整控制权(可直接改任意状态)**。

---

## 一、设计要点(一句话)

**抽奖进度与领奖进度拆成两个独立维度;领奖动作生成履约工单;发货自动通知;用户可查进度。**

```
第1层 抽奖进度(已有,不动)
  activity_prize.status : INIT(未抽奖) → RUNNING(抽奖中) → COMPLETED(已抽奖)
  驱动方:系统 / 管理员

第2层 个人领奖进度(新增,核心)
  winning_record.claim_status :
     NOT_CLAIMED(未领取) → CLAIMED(已申请待发货) → SHIPPED(已发货) → COMPLETED(已签收)
  驱动方:中奖用户(申请/确认收货) + 管理员(发货)

第3层 履约工单(复用 human_handover,仅加 type 字段)
  type=CLAIM 的工单承载处理过程:谁处理、何时处理、物流单号、备注
  状态复用: PENDING(待发货) → PROCESSING(备货中) → RESOLVED(已发货) → CLOSED(取消)
```

**为什么领奖状态不放在 `activity_prize`(重要设计取舍)**:
- `activity_prize` 的粒度是"活动 + 奖项"(一个奖项一行),而**一个奖项可能有多名中奖者**
  (实测:活动 198 一等奖有 2 名中奖者,但 activity_prize 只有 1 行)
- 一个奖项状态无法表达"张三已领、李四未领",而这正是"抽到没发货"类问题的核心
- 该字段由既有抽奖状态机(责任链/策略)+ RabbitMQ 抽奖链路 + 回滚逻辑驱动,不宜承载第二套语义
- **结论**:领奖状态放 `winning_record`(中奖者个体粒度,天然一人一行)

## 二、数据库改动

迁移脚本建议存放:`docs/design/sql/claim-fulfillment-2026-10.sql`(含回滚语句注释)

### 2.1 `user` 表 —— 默认收货地址

```sql
ALTER TABLE `user`
  ADD COLUMN receiver_name    VARCHAR(50)  NULL COMMENT '收货人姓名' AFTER status,
  ADD COLUMN receiver_phone   VARCHAR(255) NULL COMMENT '收货人手机号(Encrypt处理器加密)' AFTER receiver_name,
  ADD COLUMN receiver_address VARCHAR(500) NULL COMMENT '收货地址' AFTER receiver_phone;
```
- 手机号复用现有 `EncryptTypeHandler`(与 `user.phone_number` 一致)
- 地址明文存储,生产环境建议加密(在文档注明)

### 2.2 `winning_record` 表 —— 领奖状态 + 物流信息(核心)

```sql
ALTER TABLE winning_record
  ADD COLUMN claim_status     VARCHAR(20)  NOT NULL DEFAULT 'NOT_CLAIMED'
      COMMENT '领奖状态:NOT_CLAIMED未领取/CLAIMED已申请/SHIPPED已发货/COMPLETED已签收' AFTER winning_time,
  ADD COLUMN claim_time       DATETIME     NULL COMMENT '申请领奖时间' AFTER claim_status,
  ADD COLUMN shipping_company VARCHAR(50)  NULL COMMENT '承运公司' AFTER claim_time,
  ADD COLUMN shipping_no      VARCHAR(100) NULL COMMENT '物流单号' AFTER shipping_company,
  ADD COLUMN shipped_time     DATETIME     NULL COMMENT '发货时间' AFTER shipping_no,
  ADD COLUMN completed_time   DATETIME     NULL COMMENT '确认收货时间' AFTER shipped_time;

ALTER TABLE winning_record ADD INDEX idx_winner_claim (winner_id, claim_status);
```

**兼容性已验证**:
- `WinningRecordMapper.batchInsert` 使用**显式列名**,新增字段不影响抽奖落库
- `selectByWinnerId` / `selectByActivityId` 使用 `select *`,自动带出新字段
- 历史数据:全部保持默认 `NOT_CLAIMED`(按决策,不做批量回填)

**为什么物流字段也放这张表**:让"状态 + 物流单号"同表自洽,用户端一次查询即可显示,避免与工单联表;工单仍保留完整处理留痕。单号只有"管理员发货"这一个写入点,冗余一致性风险低。

### 2.3 `human_handover` 表 —— 工单类型

```sql
ALTER TABLE human_handover
  ADD COLUMN type VARCHAR(20) NOT NULL DEFAULT 'HANDOVER'
      COMMENT '工单类型:HANDOVER转人工/CLAIM领奖发货' AFTER session_id;

ALTER TABLE human_handover ADD INDEX idx_type_status (type, status);
```
- 默认值 `HANDOVER` → **既有转人工工单行为零影响**

## 三、状态机与流转规则

```
                用户点「我要领奖」
NOT_CLAIMED ──────────────► CLAIMED ──── 管理员登记发货 ────► SHIPPED ──── 用户确认收货 ────► COMPLETED
     ▲                          │                                │
     └──────────────────────────┴────────────────────────────────┘
              工单被取消(CLOSED)→ 状态回退为 NOT_CLAIMED(可重新申请)
```

| 迁移 | 触发者 | 同时发生 |
|---|---|---|
| NOT_CLAIMED → CLAIMED | 中奖用户 | 建 `type=CLAIM` 工单(含奖品信息 + **地址快照**) |
| CLAIMED → SHIPPED | 管理员(处理工单) | 记录物流公司/单号/发货时间;工单置 RESOLVED;**自动邮件 + 短信通知用户** |
| SHIPPED → COMPLETED | 中奖用户 | 记录确认收货时间;工单关闭(CLOSED) |
| CLAIMED → NOT_CLAIMED | 管理员取消工单 | 工单置 CLOSED,允许重新申请 |

> 可选增强(本期不做):发货 N 天后自动置 COMPLETED,需定时任务。

## 十、风险与对策

| 风险 | 对策 |
|---|---|
| 并发重复领奖 | `updateClaimStatus(id, from, to)` 带原状态条件,按影响行数判断(乐观锁) |
| 状态双写不一致(`claim_status` vs 工单 `status`) | 以 `winning_record.claim_status` 为用户可见真相;建单失败即回滚状态;工单侧变更同步回写;异常由操作日志追溯 |
| 用户改地址导致历史失真 | 建单时把地址**快照**写入工单 `question` |
| 通知失败影响主流程 | 通知放异步 try-catch,失败仅记日志,不回滚发货状态 |
| 越权领他人奖品 | 校验 `winner_id == token.userId` |
| 历史数据口径 | 按决策:全部保持「未领取」(不批量回填)。注意:历史已线下发放的记录也会显示"待领奖",必要时由管理员逐条取消工单或后续批量订正 |

## 十一、答辩话术

> 抽奖只是起点。系统包含完整的**中奖履约闭环**:未领取 → 已申请 → 已发货 → 已签收。
> 用户在中奖模块一键申请领奖,系统生成**履约工单**(与人工客服共用一套工单设施),管理员登记发货并回填物流单号,系统**自动邮件 + 短信通知**用户,用户可随时向 AI 客服查询进度,最后确认收货闭环。全流程状态可追踪、操作有日志、责任可界定。
>
