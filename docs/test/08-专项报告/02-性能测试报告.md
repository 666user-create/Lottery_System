## 5. 改造前后对比说明（诚实声明）

**⚠️ 本轮为「缺陷修复」，非「性能优化」，故未采集修复前性能基线**，原因：
1. 本轮修复内容为**参数校验与异常映射**（`@Min/@Max/@Size`、异常 handler），对被压测的 3 条读路径不构成性能影响；
2. 采集"修复前基线"需回滚代码重新编译部署，而仓库中存在业主**未提交的改动**，回滚属破坏性操作，按约定需单独授权。

**如需严格前后对比，复测方法**（同机同数据量、同脚本）：

```bash

jmeter.bat -n -t docs\test\artifacts\jmeter\lottery_system.jmx -l result_after.jtl -e -o report_after

# 2) 仅回滚校验相关文件（保留业主其他改动）
git stash push -- src/main/java/org/example/lottery_system/controller/param/PageParam.java ^
                  src/main/java/org/example/lottery_system/controller/handler/GlobalExceptionHandler.java ^
                  src/main/java/org/example/lottery_system/controller/param/UserRegisterParam.java ^
                  src/main/java/org/example/lottery_system/common/utils/RegexUtil.java

# 3) 采集"修复前"基线

# 4) 恢复修复
```

| 对比维度 | 保证措施 |
|---|---|
| 脚本一致 | 同一个 `.jmx`（token 每次重新注入） |
| 数据量一致 | 压测前核对 `user=14 / activity=5 / prize=5 / winning_record=14` |

## 6. JMeter 脚本自身缺陷与修订（本轮发现）

**首轮执行错误率 100%（3500/3500）**，根因为**脚本缺陷而非应用缺陷**：

| # | 缺陷 | 证据 | 修复 |
|---|---|---|---|
| 1 | `HeaderManager` 误写为 `HTTPSamplerProxy` 的子元素（`elementProp name="HTTPsampler.Headers"`）→ JMeter 不识别 → **token 未发送** → 全部 401 | `result.jtl` 首行：`Test failed: text expected to contain /"code":200/`，`bytes=205` | 改为 `hashTree` 下的**兄弟节点**；修订后 XML 校验 HeaderManager=3（原先 0） |
| 2 | 登录场景硬编码已清理账号 `qa_admin_16261045@test.com` | 该账号已随白名单清理删除 | 改为变量 `${loginMail}` / `${loginPassword}` |

> **经验教训**：性能脚本必须先在真实环境验证断言可通过（首轮 100% 错误即为强信号），否则会把"脚本 bug"误读为"应用性能故障"。

## 7. 结论与建议

1. **3 条核心读接口在 100 并发下零错误**，p95 ≤ 6ms，吞吐 175.6/s，性能良好；
2. 低延迟主因：活动详情与中奖记录走 Redis 缓存（`ACTIVITY_*`、`WINNING_RECORDS_*`）；
3. **未覆盖**：抽奖写接口（依赖 MQ，当前不可达，见 BUG-002）、AI 客服接口（外部 API 成本 + 长耗时）；
4. **建议**：MQ 部署后补充抽奖链路压测；生产前补充 ≥10 分钟持续压测与稳定性观察。
