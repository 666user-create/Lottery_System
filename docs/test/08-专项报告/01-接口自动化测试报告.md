## 1. 概述

以 pytest + requests 构建接口自动化套件，覆盖抽奖系统 **7 大模块 + 鉴权矩阵**，共 **147 条用例**。
断言原则（对应业主规则 #3）：**禁用只断 HTTP 200**——本项目业务失败时 HTTP 仍为 200，必须断 `body.code` 与数据正确性。

## 4. 断言强度设计（每条均已通过反向验证）

| 断言工具 | 能抓到的缺陷 | 反向验证结果 |
|---|---|---|
| `assert_code(resp, 期望码)` | HTTP 200 但业务失败（参数校验/鉴权/业务规则） | — |
| `assert_success(expect_data=True)` | `code=200` 但 `data=null` 的**假成功** | — |
| `assert_field(resp, "activityId", 34)` | 查询串号（查 34 返回别的活动） | — |
| `assert_paging_params_effective(p1, p2)` | 分页参数被静默忽略（默认值掩盖） | — |
| `assert_no_internal_leak(resp)` | SQL / 表结构 / 包路径 / 类名泄露 | ✅ 破坏兜底消息 → 失败 |
| `assert resp.code != 500`（边界） | 越界参数直穿 DB → 500 | ✅ 移除 `@Min` → 6 条失败 |
| 跨接口一致性断言 | Redis 缓存脏读 / 数据串号 | — |
| 集合运算断言（分页并集） | offset 计算错误的重复/遗漏 | — |
| 并发计数断言 | 唯一性校验竞态 | — |

**反向验证（第⑤步核心动作）**：故意破坏 3 处（邮箱正则、`@Min` 校验、异常兜底消息）后，
相关 **6 条断言如实失败**；还原后**全量 146 条恢复通过**。证明断言非"摆设"。

## 6. 工程化保障

| 机制 | 说明 |
|---|---|
| **实例指纹校验** | `app_fingerprint` fixture 校验登录页 200 + `/api/faq/list` 401，防止"测到别的系统"（2026-09-13 实际踩坑） |
| **编码加固** | `sys.stdout.reconfigure(encoding="utf-8")`；修复 `-s`/CI 重定向下 emoji 导致 **全部用例 ERROR** 的问题 |
| **数据卫生** | 固定账号复用（不累积）+ FAQ/工单用例级清理 + `db_cleanup.py` 白名单兜底（跑完实测回到 `14/0/2/0`） |
| **环境隔离** | 全部超时/地址可经环境变量覆盖，端口冲突无需改代码 |
| **反向验证标记** | `-m reverse` 预留（本次以"临时破坏 + 还原"方式在执行中完成验证） |

## 7. 结论

1. 147 条用例覆盖 7 模块 + 鉴权矩阵，**修复后 100% 通过**（1 条 xfail 为环境依赖）；
2. 断言强度经**反向验证**证明有效；
3. 测试数据零残留（白名单清理 + 自动备份）；
4. **建议**：接入 CI（如 Jenkins/GitHub Actions），在构建后自动执行 `-m smoke` 与全量回归；后续可按需接入 allure 生成可视化报告（`--alluredir=reports/allure-results`）。
