## 1. 测试策略总览

本方案定义「抽奖系统」五层测试策略，覆盖从接口到 UI 的全链路质量保障：

```
┌─────────────────────────────────────────────────────────┐
│  第 1 层  手动 Web UI 测试（端到端用户旅程）             │
│  工具：Chrome/Edge + 手工操作 + 截图证据                 │
├─────────────────────────────────────────────────────────┤
│  第 2 层  Selenium Web UI 自动化（回归保障）             │
│  工具：Selenium WebDriver 4.x + Java + ChromeDriver      │
├─────────────────────────────────────────────────────────┤
│  第 3 层  Postman 接口测试（功能 + 权限矩阵）            │
│  工具：Postman Collection v2.1（交付 JSON，可导入）      │
├─────────────────────────────────────────────────────────┤
│  第 4 层  pytest + JUnit 接口自动化（CI 回归）      │
│  工具：pytest 5.x + JUnit 5 + Maven                 │
├─────────────────────────────────────────────────────────┤
│  第 5 层  JMeter 性能测试（负载基线）                    │
│  工具：Apache JMeter 5.x（交付 .jmx 脚本）               │
└─────────────────────────────────────────────────────────┘
```

## 2. 各层测试详细策略

### 2.1 第 1 层：手动 Web UI 测试

**目标**：验证真实用户旅程的端到端可用性，覆盖页面渲染、交互、提示、跳转。

**关键用户旅程（UC）**：

| 编号 | 旅程 | 涉及页面 | 优先级 |
|---|---|---|---|
| UC-01 | 用户注册 → 登录 → 查看大厅 | user-register.html → user-login.html → user-lobby.html | P0 |
| UC-02 | 管理员登录 → 创建活动 → 关联奖品/用户 | blogin.html → admin.html → create-activity.html | P0 |
| UC-03 | 奖品管理：创建奖品 + 上传图片 | prizes-list.html → create-prizes.html | P1 |
| UC-04 | 抽奖页：发起抽奖并查看结果 | draw.html | P0 |
| UC-05 | AI 客服：知识库问答 + 转人工 | chat.html | P1 |
| UC-06 | 管理端工单处理 | admin-handover.html | P1 |
| UC-07 | 用户列表/活动列表查看 | user-list.html / activities-list.html | P2 |

**执行方式**：QA 手工操作 + 截图存档（`docs/test/artifacts/screenshots/`）+ 每步记录实际结果。

### 2.2 第 2 层：Selenium Web UI 自动化

**目标**：将核心旅程脚本化，支持版本回归时一键重跑。

**技术选型**：
- Selenium Java 4.x（`selenium-java`）
- WebDriverManager 或本地 ChromeDriver
- JUnit 5 组织用例
- Chrome 无头/有头模式

**自动化用例清单（SA-01 ~ SA-06）**：

| 编号 | 场景 | 断言要点 |
|---|---|---|
| SA-01 | 打开登录页 | 页面标题/元素可见 |
| SA-02 | 注册页表单元素 | 必填项、提交按钮存在 |
| SA-03 | 登录失败提示（错误密码） | 提示文案出现 |
| SA-04 | 聊天页加载 | 输入框/发送/转人工按钮可见 |
| SA-05 | FAQ/工单管理页（未登录跳转提示） | alert 或 401 提示 |
| SA-06 | 大厅页元素 | 活动卡片区域渲染 |

**交付**：`docs/test/artifacts/selenium/`（完整 Java 工程源码）。

### 2.3 第 3 层：Postman 接口测试

**目标**：验证全部接口的功能正确性、参数校验、权限隔离。

**Collection 结构**：

```
lottery_system.postman_collection.json
├── 00_环境变量（baseUrl、token）
├── 01_用户模块
│   ├── 注册（普通/管理员）
│   ├── 密码登录 / 短信登录
│   ├── 发送验证码
│   └── 查询用户列表 / 当前用户
├── 02_活动模块
│   ├── 创建活动
│   ├── 活动列表
│   └── 活动详情
├── 03_奖品模块
│   ├── 上传图片
│   ├── 创建奖品
│   └── 奖品列表
├── 04_抽奖模块
│   ├── 发起抽奖（MQ）
│   ├── 中奖记录（活动/奖品维度）
│   └── 我的中奖记录
├── 05_AI客服
│   ├── 工具调用聊天（SSE/同步）
│   └── RAG 聊天（SSE/同步）
├── 06_FAQ知识库（管理员）
│   ├── 新增 / 删除 / 列表
│   └── 权限用例（无token 401 / 普通用户 403）
└── 07_交接班工单
    ├── 创建（用户）
    ├── 列表（管理员，按状态）
    └── 处理（管理员）
```

**断言规范**：HTTP 状态码 + `code` 字段 + 关键 `data` 字段。

**权限矩阵**（核心设计）：

| 接口 | 无 token | 普通用户 | 管理员 |
|---|---|---|---|
| `/api/faq/*` | 401 | 403 | 200 |
| `/api/handover/list`、`/process` | 401 | 403 | 200 |
| `/api/handover/create` | 401 | 200 | 200 |
| `/activity/create`、`/prize/*`、`/user/base-user/find-list` | 401 | 403 | 200 |
| `/api/ai/chat/**`、`/api/chat/**` | 200（游客可用） | 200 | 200 |
| 登录/注册/验证码 | 200（公开） | - | - |

### 2.4 第 4 层：pytest + JUnit 接口自动化

**目标**：接口回归自动化，纳入 `mvn test` 或 CI 流水线。

**技术栈**：
- `pytest==8.3.4` + `requests==2.32.3`
- `org.junit.jupiter:junit-jupiter:5.x`
- Maven Surefire 运行

**测试类规划**：

| 测试类 | 覆盖 |
|---|---|
| `AuthApiTest` | 登录成功/失败、注册参数校验、token 有效性 |
| `FaqApiTest` | FAQ 增删查 + 权限矩阵（401/403/200） |
| `HandoverApiTest` | 工单创建/列表/处理 + 权限 |
| `ActivityApiTest` | 活动列表/详情 |
| `PrizeApiTest` | 奖品列表 |
| `DrawApiTest` | 中奖记录查询、我的记录 |

**依赖处理**：
- 接口自动化需要应用运行于 8080（`@BeforeAll` 探测，不可用则 `Assumptions.assumeTrue` 跳过，避免 CI 误报）。
- 测试数据使用独立前缀（`QA_AUTO_`），执行后清理。

**交付**：`tests/api/`（项目内真实可运行）。

### 2.5 第 5 层：JMeter 性能测试

**目标**：建立接口性能基线（响应时间/吞吐/错误率）。

**测试计划设计（lottery_system.jmx）**：

| 场景 | 线程 | 循环 | 接口 | 关注指标 |
|---|---|---|---|---|
| 登录并发 | 50 | 10 | POST /user/password/login | 吞吐 ≥ 20/s，p95 < 2s |
| 活动列表 | 100 | 20 | GET /activity/find-list | 吞吐 ≥ 50/s，p95 < 1s |
| 中奖记录查询 | 50 | 20 | POST /draw/winning-records/show | p95 < 1.5s |
| 混合场景 | 阶梯 | 持续 10min | 登录+列表+详情 | 错误率 < 1% |

**监听器**：聚合报告（Aggregate Report）、响应时间图、错误率。

**✅ 执行状态**：JMeter 5.6.3 已就位并**真实执行**（3500 请求 / 0 错误 / 175.6 次每秒 / p95 ≤ 6ms）；脚本本身修订 2 处缺陷（HeaderManager 写法、硬编码账号）后通过。详见《08-专项报告/02-性能测试报告》。

## 4. 缺陷管理流程

```
发现缺陷 → 登记缺陷报告（编号 BUG-XXX）
   → 严重级别定级（P1致命/P2严重/P3一般/P4轻微）
   → 开发修复 → 测试复测（回归）
   → 验证通过关闭 / 不通过打回
```

**缺陷定级标准**：

| 级别 | 定义 | 示例 |
|---|---|---|
| P1 致命 | 系统崩溃、数据丢失、主流程不可用、严重安全漏洞 | 登录失效、越权访问 |
| P2 严重 | 核心功能异常、无降级处理、性能严重不达标 | 抽奖接口 MQ 不可达时 30s 超时 |
| P3 一般 | 功能可用但有偏差、提示不友好 | 错误码语义模糊 |
| P4 轻微 | 文案、样式、体验细节 | 提示语不统一 |
